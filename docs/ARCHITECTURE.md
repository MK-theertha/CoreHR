# CoreHR — How It Works

A workforce management platform — employee directory, leave approvals, notifications, and a role-scoped dashboard — built as a two-package npm workspace with a real Postgres database behind it, no mock data anywhere in the loop.

Stack: Express 5 · Prisma 7 (`@prisma/adapter-pg`) · PostgreSQL · JWT (access + refresh) · React 19 · Vite · TanStack Query · Zod

> This document is generated by reading the current backend routes/services and frontend App shell directly, not from `README.md` (which predates the Reports and Organization modules).

## 1. Overview

CoreHR is split into two npm workspaces, `backend` and `frontend`, wired together by one contract: JSON over HTTP at `/api/v1/*`, authenticated with a bearer JWT. The backend owns every business rule — who can see which employees, who can approve whose leave — the frontend is a thin, role-aware client over that API.

Everything in the system fans out from four ideas: an **Organization** (single-tenant today, schema supports more), **Users** who log in, **Employees** who are HR records optionally linked to a User, and a **Role** on every User that the API checks on almost every route.

## 2. Monorepo layout

Root `package.json` declares npm workspaces for `frontend` and `backend`; each has its own dependencies and scripts, run independently in dev.

```
backend/
  prisma/schema.prisma   # data model — source of truth
  prisma/seed.ts         # org, departments, 3 login accounts, sample leave + notification
  src/config/            # env.ts, prisma.ts (pg driver adapter), swagger.ts
  src/controllers/       # one per domain — parse req, call service, shape response
  src/services/          # Prisma queries + business rules live here
  src/routes/            # Express routers — protect + authorize + zod validate, per route
  src/middleware/        # protect (JWT), authorize (role gate), validate (zod), errorHandler
frontend/
  src/pages/             # one page per top-level route
  src/hooks/             # TanStack Query hooks per domain + useAuth, useTheme
  src/components/        # layout shell, data-table, domain widgets, ui/ primitives
  src/lib/api.ts         # apiFetch (public) + authFetch (bearer token, 401 refresh-retry)
  src/types/index.ts     # TS types mirroring API response shapes
```

## 3. Data model

Defined in `backend/prisma/schema.prisma`. Seven models; `AuditLog` exists in the schema but nothing writes to it yet.

| Model | What it is | Notes |
|---|---|---|
| **Organization** | Top-level tenant. Everything else belongs to one. | Only one is seeded today. |
| **User** | Login identity — email + bcrypt hash + role. | Optionally linked 1:1 to an Employee. Role: `SUPER_ADMIN` / `HR_ADMIN` / `MANAGER` / `EMPLOYEE`. |
| **Employee** | The HR record — name, contact, job title, department, status. | May or may not have a linked User. Status: `ACTIVE` / `PROBATION` / `INACTIVE` / `TERMINATED`. |
| **Department** | Belongs to an Organization, has many Employees. | "Manager" is derived, not stored — see below. |
| **LeaveRequest** | Belongs to an Employee. | Optional approver User via the `LeaveApprover` relation. Status: `PENDING` / `APPROVED` / `REJECTED` / `CANCELLED`. |
| **Notification** | Belongs to a User. | Auto-created only when a leave request is approved or rejected. |
| **AuditLog** | Present in the schema for future use. | No controller, service, or route writes to it today. |

> **Not a stored field:** a department's "manager" shown in the UI is computed on read — `department.service.ts` queries for the first Employee in that department whose linked User has role `MANAGER`. There's no `managerId` column.

## 4. Request lifecycle

Every API request passes through the same pipeline, in `app.ts` then the matched router:

1. **helmet + cors** — security headers; origin allow-list from `CLIENT_URL`, plus any `http://localhost:*` in development.
2. **express.json()** — parses the body, 1MB cap.
3. **morgan** — request logging — `dev` format locally, `combined` in production.
4. **router match** — one of nine routers mounted under `/api/v1`.
5. **protect** — verifies the `Bearer` JWT against `JWT_ACCESS_SECRET`; attaches `req.user`. Skipped only on register/login/refresh.
6. **authorize(...roles)** — rejects with 403 if `req.user.role` isn't in the allowed list for that route.
7. **validate(schema)** — Zod-parses `req.body`; 400 with issue list on failure, otherwise replaces `req.body` with the parsed value.
8. **controller → service** — controller shapes the HTTP response; the service holds the Prisma query and the actual business rule.
9. **errorHandler** — anything thrown as `AppError` returns its status + message; anything else becomes a generic 500 (stack trace only in development).

Controllers wrap every handler in `asyncHandler`, so a thrown `AppError` (or any rejected promise) always reaches `errorHandler` instead of crashing the process.

## 5. Auth & tokens

Two JWTs, signed with separate secrets: a short-lived access token and a longer-lived refresh token. Neither is stored server-side — sessions are stateless.

**Login:** `POST /auth/login` → `bcrypt.compare()` → issue access token (15m) + refresh token (7d) → client stores both.

**Every authenticated call:** the frontend's `authFetch` attaches `Authorization: Bearer <access token>`. On a **401**, it transparently calls `POST /auth/refresh` with the stored refresh token, retries the original request once with the new access token, and only forces a logout (dispatching a `corehr:unauthorized` event that `App.tsx` listens for) if the refresh itself fails.

**Registration is deliberately narrow:** `POST /auth/register` always creates an `EMPLOYEE`-role account — there is no public path to a privileged role. It also has a quiet linking behavior worth knowing: if an `Employee` row already exists with the same email (e.g. HR pre-created the HR record before the person signed up) and isn't linked to a User yet, registration links the new User to that existing Employee rather than creating a duplicate.

**Token storage:** tokens live in `localStorage` if "remember me" was checked at login, otherwise `sessionStorage` — never both at once; `setTokens()` explicitly clears the other store on write.

## 6. Roles & permissions

Enforced entirely server-side, per route, via `authorize(...roles)` — the frontend nav just hides links a role can't use, it isn't the security boundary.

| Area | SUPER_ADMIN / HR_ADMIN | MANAGER | EMPLOYEE |
|---|---|---|---|
| Employee directory | full CRUD | read-only, own department only | no list access |
| Own employee record | view + edit | view + edit | view + edit (phone / gender / DOB only) |
| Departments | full CRUD (delete: SUPER_ADMIN only) | read-only | read-only |
| Leave requests | view all, approve/reject any | view all, approve/reject others' (not own) | apply, view + cancel own pending |
| Notifications | own | own | own |
| Dashboard | org-wide summary + trends + activity | org-wide summary + trends + activity | personal counts only |
| Reports | SUPER_ADMIN only | — | — |
| Organization settings | SUPER_ADMIN only | — | — |
| Role management | SUPER_ADMIN only | — | — |

> **A leave decision cannot be self-approved:** `leave.service.ts` checks `employee.userId === approverUserId` and throws a 403 even if the approver otherwise has permission — a manager can approve a report's leave, never their own.

## 7. API reference

Base path `/api/v1`. Everything except the three auth-entry routes requires `Authorization: Bearer <token>`. Interactive docs are also served live at `/api-docs` (Swagger UI). Every response has the shape `{ success: boolean, data: T }`; validation failures return `{ success: false, message, errors }` with the Zod issue list.

### Auth
| Method | Path | Access |
|---|---|---|
| POST | `/auth/register` | public — always creates an EMPLOYEE |
| POST | `/auth/login` | public — returns user + accessToken + refreshToken |
| POST | `/auth/refresh` | public — exchanges refreshToken for a new accessToken |
| GET | `/auth/me` | any authenticated user |

### Employees

| GET | `/employees/:id` | SUPER_ADMIN, HR_ADMIN, MANAGER |
| POST | `/employees` | SUPER_ADMIN, HR_ADMIN |

## 8. App shell & routing (frontend)

`App.tsx` is the entire routing and session brain — there's no router config file elsewhere.

- On mount, if an access token exists in storage, it calls `GET /auth/me` to rehydrate the session; otherwise it renders the logged-out routes.
- **Logged out:** only `/login` and `/signup` resolve; everything else redirects to `/login`.
- **Logged in:** every route nests under `AppShell` (sidebar + topbar + `<Outlet />`), and `/login` / `/signup` redirect to `/dashboard` instead.
- All pages are `lazy()`-loaded and wrapped in a shared `<Suspense>` skeleton inside `AppShell`.
- A global `corehr:unauthorized` window event (fired by `lib/api.ts` when token refresh fails) is the only other thing that can force a logout mid-session.

Role-based nav is a single data file, `components/layout/nav-items.ts` — each entry lists the roles allowed to see it, and the sidebar filters against `user.role`. This is UX only; the real gate is server-side `authorize()`.

## 9. Data fetching

All server state goes through TanStack Query, one hook file per domain (`useEmployees`, `useLeave`, `useDepartments`, `useDashboard`, `useNotifications`, `useReports`, `useOrganization`, `useProfile`). The pattern repeats everywhere:

- a `useQuery` keyed by `['domain']` or `['domain', id]`, calling `authFetch`
- `useMutation` hooks for create/update/delete that call `queryClient.invalidateQueries` on success — usually invalidating both their own domain and `['dashboard']`, since most actions move a dashboard count

`lib/api.ts` is the only place that talks to `fetch` directly: `apiFetch` for the three public auth routes, `authFetch` for everything else, with the 401 → refresh → retry-once logic described in [Auth & tokens](#5-auth--tokens) living entirely inside it. No component ever touches tokens directly.

## 10. Running it

1. `docker compose up -d postgres`
2. Backend: `cd backend && npm install && npx prisma migrate dev && npm run prisma:seed && npm run dev` → http://localhost:4000
3. Frontend: `cd frontend && npm install && npm run dev` → http://localhost:5173

A full-stack Docker Compose path also exists (`docker compose up --build`) but doesn't run migrations/seed automatically — see the root `README.md` for details and the seeded login accounts.

## 11. Known gaps

- No document/compliance module; the schema anticipates one, the API doesn't expose it.
- `AuditLog` is schema-only — nothing writes to it yet, despite audit-relevant actions (role changes, leave decisions) existing.
- Redis is provisioned in Compose but nothing in the app uses it.
- Single-organization in practice — the schema supports multiple tenants, but nothing creates a second one, and several services (`employee.create`, `department.create`) just grab `organization.findFirst()`.
- A department's "manager" is inferred (first employee whose linked user has role MANAGER) rather than explicitly assigned — a department with two managers will silently show whichever one Prisma returns first.
